`gh nibfin` is a [GitHub CLI](https://cli.github.com/) extension. It uses the
account `gh` is logged in with and never switches it.

A command that changes something first shows its plan: every item it
considers, with `[no change]` for those already in place. It asks you to confirm
and then reads every change back. `--yes` skips the question. `pause` and
`resume` ask nothing, and `status` only reads. The [Dashboard](../setup/#dashboard)
runs the same commands with the same plans.

An error prints as `<code>: <message>` and exits with status 1. The code names
the original cause and the message says what to do next; see
[Common failure codes](#common-failure-codes).

The reference below is generated from the commands' own definition, the same
source the Dashboard builds its forms from, so it always matches the CLI.

## Troubleshooting

### Recovering from `pending`

Nibfin adds `pending` when an Issue needs a person, for example a stage that
stopped, an expired login, low memory on the Runner host or a rejected push.
While `pending` is present, nothing runs for that Issue.

1. Open the Issue, or its pull request, and read Nibfin's comment. It names the
   cause code, the message and the run, whose log has the full output.
2. Fix the cause the comment names. A comment that says the failure _looks
   temporary_ (a network or GitHub error, or a single agent run that went
   wrong) needs no fix.
3. Remove the `pending` label, or run `gh nibfin resume <issue>`, which also
   removes `pause`. Nibfin reads the Issue's state from GitHub again and
   reruns the unfinished stage.

There is no retry limit: every stage that stops leaves `pending` with its
comment. A Job that never started, such as one that waited too long for an
offline Runner, leaves none; see [An offline Runner](#an-offline-runner).

### Common failure codes

Codes from `gh nibfin` on your host:

- `podman_missing`: Podman is not installed. [Install Podman](https://podman.io/docs/installation); gh nibfin never installs system software.
- `machine_missing`: Windows or macOS has no `podman machine`. Run `podman machine init`.
- `machine_start_failed`: The `podman machine` did not start. Start it with `podman machine start` and read its error.
- `machine_stopped`: `status` could not read a part because the machine is stopped. `status` never starts it; see [An offline Runner](#an-offline-runner).
- `no_runners`: The host has no Runner of that provider. Run `gh nibfin runner add <provider>` first.
- `not_logged_in`: The provider CLI is not logged in after `login` or `runner add`. Run `gh nibfin login <provider>` again.
- `scope_missing`: Your `gh` login lacks a scope the command needs. Run `gh auth refresh -s workflow`.
- `not_initialized`: `upgrade` found no Nibfin workflows. Run `gh nibfin init` first.
- `runner_repo_conflict`: The host's Runners serve another repository than the plan expects. All Runners on a host serve one execution repository; plan again from it.
- `runner_install_failed`: A Runner could not be installed, for example a refused `sudo` in the VM. Run the command the message names inside the VM, then `runner add` again.
- `autostart_failed`: The task or LaunchAgent that keeps the machine up could not be set. Read the message; nothing after it was changed.
- `unsupported_host`: The host lacks something a Runner needs, such as WSL 2 or `git` and `ssh` for a private repository. Install what the message names, for example `wsl --update`.
- `ssh_key_missing`: A collaborator has no SSH key on their GitHub account. Run `ssh-keygen -t ed25519` and `gh ssh-key add ~/.ssh/id_ed25519.pub`, then `runner add` again.
- `ssh_key_locked`: The SSH key's passphrase could not be asked or was wrong three times. Run `runner add` in a terminal.
- `runner_request_refused`: The runner request was refused, for example without write access. Ask the repository's Owner to add you as a collaborator with write access.
- `runner_request_timeout`: The runner request got no answer within 10 minutes. Run `runner add` again.
- `runner_request_failed`: The request Issue was closed, or its answer could not be read. Run `runner add` again.
- `runner_busy`: GitHub reports a Runner busy but no Job of it runs on this host. Run `runner remove` again later to finish it.
- `listen_failed`: The Dashboard's port is taken. Use another `--port`, or leave it out for any free port.
- `proof_invalid`: The Dashboard's session URL was wrong or already used. Restart `gh nibfin dashboard` for a new URL.

Codes in a `pending` comment from a Job:

- `STAGE_BLOCKED`: The stage stopped and named something only a person can decide or supply. Read the comment, answer or fix it on the Issue, then remove `pending`.
- `STAGE_PROTECTED_PATH`: The branch changed a [protected path](../setup/#protected-paths). Change that path through your own maintenance route, then remove `pending`.
- `STAGE_PUSH_REJECTED`: GitHub rejected the push of the branch. Check the branch's rules and its remote head, then remove `pending`.
- `STAGE_HOST_MEMORY_LOW`: The Runner host had too little free memory to start an agent. Free memory or lower the number of Runners, then remove `pending`.
- `STAGE_NO_PROGRESS`: The stage ended without progress, and the same stage would run again. Read the comment and the run log, fix what they name, then remove `pending`.
- `AGENT_USAGE_LIMIT`: The provider's usage limit was reached. Remove `pending` after the reset time the comment gives.
- `GITHUB_READ_FAILED`: A read from GitHub failed. Usually temporary: remove `pending` to retry.

### An offline Runner

`gh nibfin status` shows the host: whether the `podman machine` runs, each
Runner's service, and GitHub's online, offline and busy state for it.

- **Windows and macOS.** The Runners run inside the `podman machine`, so they
  are offline whenever it is stopped. Run `podman machine start`. `runner add`
  set up the Windows task `Nibfin podman machine` or the macOS LaunchAgent that
  starts it at login (and on Windows, on resume from sleep); `status` reports
  it as `present`, `outdated` or `absent`. Run `runner add` again to restore
  it.
- **Linux.** The Runners are systemd user services with linger, so they run from
  boot. A stopped service shows as not active in `status`.
- **A collaborator's Runners.** Reading GitHub's online state needs admin of the
  execution repository, so `status` shows only the local service, with GitHub
  as `needs admin`.

A Job assigned while every Runner of its Assignee is offline waits in GitHub's
queue for one of them to come online. It is not moved to someone else.

GitHub ends a Job that waits longer than its queue limit for self-hosted
Runners. That Job never started, so Nibfin adds no `pending` and the Issue
waits. Once a Runner is online, wake the Issue with a label change, for example
`gh nibfin pause <issue>` and then `gh nibfin resume <issue>`.
